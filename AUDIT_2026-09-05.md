# Cross-Platform Codebase Audit — LLM_Ecosystem (Windows) × qwen-serving (WSL)

**Date:** 2026-09-05 · **Auditor:** autonomous coworker dispatch (full-text-only)
**Scope:** `D:\LLM_Ecosystem` (Windows workspace, git), `~/qwen-serving` (WSL fork of syv-ai/qwen38-27b-rtx3090), `scripts/wsl` launcher layer, runtime state under `~/.qwen` and `C:\Users\Apath\.qwen`.
**Method:** source-level read of every script in the operational path; `git log -S` archaeology for removed features; live inspection of on-disk runtime state. No file was modified during this audit.

---

## 0. Executive Summary

The stack is healthier than its iteration history suggests: the vLLM serving repo is a well-maintained upstream fork, and the modularized `mcp-qwen` (`076456b`) is clean. However, the audit found **one critical loss, four unobservable-failure classes, and a pile of migration leftovers**:

1. **CRITICAL — the engine-wedge detector/auto-heal was deleted in `de01aa9` (2026-09-03) while all three user-facing documents still advertise it** (README §4, `package.json` description, `qwen_server` tool description). The removed code was the field-proven defense against the 4.5-hour GPU-burning engine hangs of 2026-08-28/29. A wedge today costs 240 s of dead GPU time per dispatch, forever, and `qwen_server status` affirmatively misreports health.
2. **The stream proxy converts vLLM errors into *successful-looking* completions** with markers that no downstream detector matches — a failed mid-stream request is reported as a completed task with the error text buried in the model output.
3. **The "machine-wide" goose semaphore is actually per-OS**: lease/task state is keyed on `os.homedir()`, so a Windows-side and a WSL-side MCP instance each keep independent slot pools, task stores, and can even both bind port 18021 (separate WSL2/Windows loopback namespaces) and both claim to own it.
4. **Slot-directory migration** (`~/.qwen/goose_slots` → `~/.qwen/tasks/goose_slots`) was never propagated to the test suite or fully cleaned from the kill script — `test_global_semaphore.js` now "cleans stale leases" in a directory production no longer uses.
5. A set of **dead files** (2.5 GB Open WebUI `.venv`, 661 KB orphan `last_start.log`, empty `.mcp.json`, fossil `.engine_heal.lock`, broken `alternative.sh`) and **doc drift** (race 45 s vs 150 s, timeout 1 h vs 4 h, `MAX_SEQS` 1 vs 8, version 4.5.3 vs 4.5.6).

## 2. Backward-compatibility layers & obsolete fallbacks to prune

### 2.1 `test_global_semaphore.js` — tests a path production abandoned
- `const SLOT_DIR = path.join(os.homedir(), ".qwen", "goose_slots")` is the **pre-v4.5.6** lease directory. Current `src/config.js` defines `SLOTS_DIR = ~/.qwen/tasks/goose_slots`.
- Consequence: the "wipe leftover leases" step (`fs.rmSync(SLOT_DIR, {recursive:true})`) removes the *wrong* directory, so the test's precondition cleanup is a no-op, and any stale lease in the real directory makes the test fail nondeterministically. The cross-process exclusion assertions themselves still run against the correct directory (they import from `index.js`), but the safety net is dead.
- **Fix:** point `SLOT_DIR` at `SLOTS_DIR` from `config.js` (import it; don't recompute).

### 2.2 `scripts/wsl/kill_all_tasks.sh` — purges three lease directories, one of which is obsolete
Purges `~/.qwen/tasks/goose_slots` (current), `~/.qwen/goose_slots` (obsolete — keep for one more migration cycle, then prune), and `/mnt/c/Users/Apath/.qwen/tasks/goose_slots` (the **Windows-home** directory — legitimately different, see §4.3). The middle entry is the only pure cruft; the triple-purge is a visible symptom of the path migration.

### 2.3 `scripts/wsl/wait_ready.sh` — stale log + always-exit-0
- Line 15 tails `~/qwen-serving/last_start.log` (no writer exists — §1). The useful tail is `/tmp/mcp_launch_huge.log`.
- The script's final statement on timeout is `tail ... || true` → **exit code 0 on failure**. Any caller chaining off `wait_ready.sh` cannot tell "READY" from "TIMEOUT" programmatically; only the echoed text differs.
- Line 13's `tr '\0' '\n' < /proc/$PID/environ | grep -i LOOKUP_ADAPTIVE` is a one-off A/B diagnostic left in a production helper.
- **Fix:** `exit 1` on timeout; tail the real log; drop the environ probe.

### 2.4 `avo_runner.py` — dead key path + legacy lineage shim
- `get_api_key()` reads `~/qwen-serving/api_key.txt`; run on Windows that resolves to `C:\Users\Apath\qwen-serving\api_key.txt` (does not exist — the repo lives in WSL), run in WSL the file is `.disabled`. The key is effectively always empty; it works only because the server is unauthenticated (§1).
- `lineage_brief()` carries a "back-compat with the pre-engine `history` schema" shim (id/metric keys). No lineage file on disk uses the old shape — prune, or at least confirm with one `grep -l '"history"' ~/.qwen ... .avo/lineage.json` sweep.

### 2.5 `alternative.sh` (qwen-serving, upstream-derived) — broken on this machine
`export VLLM_API_KEY="$(cat api_key.txt)"` under `set -e` → the script dies the moment the key file is absent, which is the current state. If this fork is meant to stay runnable here, guard the cat like `single-user/start_qwen.sh` does (`[ -f ... ] && export ...`); otherwise document it as upstream-only.

### 2.6 `update_schemas.py` vs `setup_links.sh` — duplicated config writers, drifting content
Both write `~/.gemini/config/mcp_config.json` (Windows master + WSL copy) with a `QWEN_RACE_MS` env block. Today they agree on `150000`, but they are two generators that can diverge (each already disagrees with the *other* surfaces — §5.1). Consolidate into one canonical config template + a single applier, or have `update_schemas.py` stop writing config and only write schema/instruction files.

### 2.7 `qwen_coworker` prompt directives — hard-coded platform assumptions
`goose_runner.js` embeds "Use `write`/`edit`/`tree`/`shell` (bash)" directives that only describe the *developer* extension's toolset, and the Windows-branch adds a CRLF note while the WSL-branch adds a POSIX note — fine — but `isWslLocation()` treats **any** `/home/`, `/root/`, `/etc/`, `/var/`, `/usr/`, `/tmp/` prefix as WSL. On a WSL-hosted MCP instance every POSIX path (including `/mnt/d/...`) is "in WSL" (harmless there); on a Windows-hosted instance a user passing `/tmp/foo` is silently routed into WSL. Low risk, but it is a fallback-by-heuristic rather than an explicit target parameter.

## 3. Cross-platform code duplication

### 3.1 The launcher layer is inverted: WSL repo is a shell over the Windows drive
Canonical launcher scripts live in `D:\LLM_Ecosystem\scripts\wsl\` and are **symlinked** into `~/qwen-serving/launchers/` (untracked) by `setup_links.sh`. The same is true of `stream_proxy.js` (symlink `~/qwen-serving/stream_proxy.js` → `/mnt/d/.../mcp-qwen/stream_proxy.js`), the WSL MCP config (`node /mnt/d/LLM_Ecosystem/mcp-qwen/index.js`), and even WSL's `~/.claude/CLAUDE.md` / `~/.gemini/GEMINI.md` (symlinks into `C:\Users\Apath\`).

Implications:
- **The entire Node layer of the WSL serving stack physically lives on the 9p-mounted Windows drive.** If Windows is asleep or the D: mount drops, WSL-side serving is dead — there is no WSL-resident fallback copy.
- `ensureStreamProxyRunning()` in `server_lifecycle.js` spawns the proxy from `__dirname/../stream_proxy.js` (i.e., the `/mnt/d` copy directly) while the launchers spawn `~/qwen-serving/stream_proxy.js` (the symlink to the same file). Two spawn sites, two pkill patterns, no coordination — a racing-restart pair (launcher pkill's a proxy that the MCP supervisor just launched; the MCP supervisor's `/health` check can then "reuse" the launcher's instance — the `EADDRINUSE → exit 0` path in `stream_proxy.js` has **no health check on the reused instance**).
- The clean direction (Windows `.bat` → thin `wsl -d Ubuntu -- bash` wrapper, commit `c340954`) is the model; the symlink farm goes the other way. Consider making `~/qwen-serving` the canonical home for launchers/proxy (tracked in the fork's `launchers/`) and symlinking into `D:` instead — the serving repo is where the operational context (venv, patches, model) already is.

### 3.2 Kill/stop logic exists in five variants
1. `scripts/main/kill_all_tasks.bat` (taskkill goose + wsl call)
2. `scripts/wsl/kill_all_tasks.sh` (curl cancel_all + pkill goose/avo + rm 3 lease dirs)
3. `scripts/wsl/stop_server.sh` (pkill vllm/EngineCore/stream_proxy)
4. `start_huge.sh` / `start_fast.sh` inline `pkill -9` of the same three patterns (self-pre-emption before each boot)
5. MCP `cancelAllTasks()` in `task_registry.js` (in-memory cancel + disk cancel + machine-wide pkill + lease clear) and `qwen_server stop` (which *also* calls `cancelAllTasks` before `stopServer`)

The pkill pattern strings (`'vllm serve'`, `'EngineCore'`, `'stream_proxy.js'`, `'goose run'`) are repeated verbatim in at least 7 files. Consolidation candidate: one canonical `ops.sh` with `stop_server`/`kill_tasks`/`purge_leases` functions that both the `.bat` wrappers and the MCP call; keep the MCP's HTTP-first cancel but make it the sole process-killer.

### 3.3 Patch-application logic in three places
- `scripts/wsl/apply_patches.sh` (skip-`dflash2-backport` special case, idempotent reverse-dry-run, then `kvarn/install.sh`, then `verify.sh --no-server`)
- `Dockerfile` inline loop (same skip, no idempotency, `verify.sh --install` gate)
- `patches/_check_applied.py` + `verify.sh` content checks
The `dflash2-backport.patch` skip is copy-pasted in two places and the patch is still in the tree (33 KB) — it's "skipped" in both appliers but still shipped, still in `verify.sh`'s `superseded_by()` bookkeeping. Either delete the patch file or let the appliers declare skip-lists from one shared source.

### 3.4 The uncensored stack is a second, convention-only serving family
`scripts/uncensored/` (llama.cpp Windows) and `scripts/main/` (vLLM WSL) share port 18020 and the model name `qwen3.8-27b`; exclusivity is enforced **only by comments** ("stop that first"). `status.bat` disambiguates manually. Two different engines, two different tool-call parsers (llama.cpp's OpenAI-compat vs vLLM's `qwen3_coder` XML parser), both behind the same name — a goose session resumed across a server-family switch would silently change tool-call behavior.
Additionally, `llama-cpp/boot.err.log` records **20 "model has unused tensor blk.64.* — ignoring" warnings** (the GGUF's 65th block — attention q/k/v/o, FFN, and MTP tensors, ~350 MB total — is not wired into llama.cpp's arch definition). If `n_layer` in the arch is 64, the served uncensored model is silently missing its last layer. Worth a one-line perplexity sanity check before this stack is trusted again.

### 3.5 API-key lookup in four places, each with its own candidate list
`wsl_bridge.getApiKeySync()` (3 Windows + 2 WSL candidates), `avo_runner.get_api_key()` (WSL-home path), `quality_battery._key()` (optional header), `start_qwen.sh` (`api_key.txt` if present). All four currently resolve to *nothing* because the file is `.disabled` (§1). One `keyutil.sh`/`keyutil.js` or a documented "we run unauthenticated, bind 127.0.0.1" decision would retire the whole cluster.

### 3.6 Two goose binaries, two session stores
WSL `~/.local/bin/goose` (Jun 26 build, 292 MB) and Windows `C:\Users\Apath\.local\bin\goose.exe` (Aug 23 build, 265 MB) are **different versions**; goose session storage is per-OS-home. A named session created by a WSL dispatch cannot be `--resume`d by a Windows dispatch and vice versa, so the "milestone session" protocol (§5 of README) silently breaks whenever the dispatching surface changes OS. At minimum: pin one goose version and install it on both sides; document the session-store split.

## 4. Architectural weaknesses → unobservable failure modes

Ranked by blast radius.

### 4.1 Engine wedge is undetectable again (CRITICAL)
**What was removed in `de01aa9`** (`git show de01aa9 -- mcp-qwen/index.js`, −473 lines):
- `canaryProbe()` — end-to-end completion probe, 60 s cache (the *authoritative* wedge signal; the removed comments note a 1-token canary can pass on a degraded engine — the 2026-08-28 post-unwedge canary squeezed through at 5.5 tok/s)
- `engineWedgeState()` — stats-line silence > `QWEN_WEDGE_SILENCE_S` (120 s default) while port answers = wedged
- `ensureEngineWarmed()` — 24 k-token synthetic warmup (3 attempts × 420 s) riding out the first-large-prefill stall, with dispatch refusal when warmup fails
- `.engine_heal.lock` cross-instance heal guard; `QWEN_AUTO_HEAL=0` kill-switch; `already_running_wedged` / `restarted_wedged_engine` statuses
- The pre-dispatch gate in `ensureServerRunning()`

The commit message lumps this as "obsolete issue #48 warmup/wedge code." The **warmup** was indeed the interim mitigation for #48 (JIT-on-first-shape stall), now fixed upstream (`05d1a0e`, `201d237`). The **wedge detector** was the generic defense against engine-core hangs — the 2026-08-28 incident class (KVarN OOB-read / WSL2 IMA / upstream #34 fp8 Xid-31 / any future deadlock) — which the 2026-08-29 notes explicitly say is **not fully eliminated** ("the pristine kernel only rarely wedges").

**What replaced it:** `serverInfo()` = 2 s-timeout `GET /v1/models`; `warmEngine()` = a **1-token ping** (exactly the signal the removed code documented as insufficient). `qwen_server status` reports `running` on a wedged engine.

**Failure sequence today if a wedge recurs:** each dispatch burns 240 s (first-token timeout) of 100 % GPU, the task is killed with a correct message, the *next* dispatch repeats it, `qwen_server status` says `running`, and recovery requires a human to notice and call `stop`/`start`. The 2026-08-28 incident was 4.5 h of this with the detector absent; it was re-introduced exactly because the detector was absent.
**Fix (restore, don't reinvent):** `git show de01aa9^:mcp-qwen/index.js` still contains the complete implementation; port `canaryProbe` + `engineWedgeState` + the pre-dispatch gate into `src/server_lifecycle.js` (the 24 k warmup can stay removed if the upstream prewarm patches are trusted, but the *silence* detector must come back). Then update README §4, `package.json`, and the `qwen_server` tool description to match reality (or remove those claims).

### 4.2 The stream proxy converts errors into successful completions
`stream_proxy.js` rewrites three failure classes into *valid* SSE completions with `finish_reason: "stop"` + `[DONE]`:
- upstream HTTP ≥ 400 → content `\n\n[vLLM Error: ...]`
- mid-stream error JSON (no `choices`) → content `\n\n[vLLM Mid-Stream Warning: ...]`
- upstream socket error → content `\n\n[vLLM Upstream Stream Interrupted: ...]`
- plus its own repetition circuit-breaker → `[StreamProxy Guard: ...]`

Downstream, `summarizeGooseRun()`'s `isStreamError` regex matches only `/Stream decode error|error decoding response body|Network error:.../` — **none of the four markers match** — so `isError` stays false and the task is reported *completed* with the error text buried mid-message. The repetition watchdog in `goose_runner.js` (34+ repeated chars on the 2000-char tail) is a *second, independently-thresholded* breaker at a different layer than the proxy's `RepetitionDetector` (35 chars / 18× unit patterns) — the same degenerate stream can trip one and not the other, and the proxy-side trip silently truncates the stream while the run-side trip kills the process.
**Fix:** (a) make the proxy emit a distinguishable terminal signal (e.g., a `data:` JSON with a non-OpenAI sentinel, or a dedicated SSE comment `# stream-proxy-error: <class>`) that the runner parses into `isError`; (b) collapse the two repetition detectors into one, on the runner side only (the proxy should stay dumb); (c) log the conversion to `/tmp/stream_proxy.log` (currently the only trace is a `console.error` line for the breaker).

### 4.3 "Machine-wide" semaphore is per-OS; port 18021 can be double-bound
Lease files and task JSONs live under `os.homedir()`: `C:\Users\Apath\.qwen\...` for the Windows-hosted instance, `/home/apath/.qwen/...` for the WSL-hosted instance (both instances run *the same script file* on `/mnt/d`, but with different `homedir()`). Consequences:
- A Windows and a WSL MCP instance each think they hold the sole global slot → up to 2 concurrent goose processes machine-wide, defeating `MAX_CONCURRENT_GOOSE=1` (engine `MAX_SEQS=1` would then queue the second *inside* vLLM — the invisible queue the README itself warns about).
- `pidAlive()` is cross-OS always-false (separate PID namespaces): each platform's leases look dead to the other after heartbeat staleness (5 min) — reclamation is "safe" only by accident.
- Port 18021 can be bound **simultaneously** in the Windows loopback and the WSL2 loopback namespaces; each instance reports `status_endpoint_owned_by_this_instance: true`. `wait_command` (`curl 127.0.0.1:18021/...`) delivered by one platform never reaches the other's instance — a cross-platform task is invisible (404) and its long-poll can hang up to the 4 h `DEFAULT_TIMEOUT_MS` disk-poll bound.
- `kill_all_tasks.sh`'s triple-dir purge and the Windows-home candidate in `getApiKeySync()` are both patch-mitigations for exactly this split.
**Fix:** pick one canonical state root (e.g., always `/mnt/d/LLM_Ecosystem/.runtime/` or `C:\Users\Apath\.qwen` via UNC, both OSes can see it) or make the root an explicit `QWEN_STATE_DIR` env in *both* MCP configs. Document that only one platform's instance may be active at a time, or make the status port 127.0.0.1-only per namespace and add a platform tag to leases.

### 4.4 MCP shutdown kills nothing
`index.js` lifecycle: `process.once("SIGTERM"/"SIGINT"/stdin close)` → `cleanup()` → `process.exit(0)`. `cleanup()` calls `killProcessTree()` which fires **async** `execFile` (Windows: `wsl.exe ... pkill` / `taskkill`; WSL: `pkill`) and then `process.exit(0)` runs immediately — the spawned killers are children of the dying process and never execute. Graceful MCP shutdown (IDE closing a session) therefore **orphans every in-flight goose process**; only the emergency kill script (or the next dispatch's first-token timeout) reaps them. The status HTTP server is also never `.close()`d (moot while `exit(0)` is in play, but it makes `beforeExit` unreachable).
**Fix:** make the SIGTERM path synchronous (`child_process.execFileSync` / `pkill` sync variants) or exit with a grace delay; at minimum, `process.kill(-pid)` is synchronous on the WSL side — use it.

### 4.5 `ensureServerRunning()` clobbers manual servers and boots only one mode
- It fires only when `currentMode()` returns null (server down). If a *manual* `start_fast` server is up, the first MCP dispatch passes (`already_running`) — fine. But if the server is down, it unconditionally runs `launchers/start_huge.sh`, which begins with `pkill -9` of any `vllm serve`/`EngineCore`/`stream_proxy.js` — an auto-start from MCP therefore *kills* anything a human left half-started, and can never produce a `fast` server (`qwen_server start` is hardcoded to huge; `start_fast.bat` is the only path to a fast server).
- It redirects to `/tmp/mcp_launch_huge.log` — the file the removed wedge detector used to parse. Today **nothing reads it**; a wedged engine's only trace is a log nobody watches. (Also `/tmp` is ephemeral across WSL updates.)
**Fix:** respect a `QWEN_DEFAULT_CTX` env (default `huge`) so both modes are MCP-reachable; move the launch log to a durable path the status tool can tail.

### 4.6 `GOOSE_WORKING_DIR` missing from the Windows→WSL spawn branch (pre-existing)
The documented fix for the fabricated-path bug (NOTES.md "Bug: fabricated file path", goose#6610 — "the developer extension reads `GOOSE_WORKING_DIR`, not `current_dir()`") is applied to the native-WSL and native-Windows spawn branches but **not** to the Windows-host→WSL-target branch (`wslEnv` in `goose_runner.js`; identical gap in the pre-refactor monolith, so this is not a modularization regression). That branch currently relies on `wsl --cd`, which per #6610 is exactly the signal goose ignores. The defensive "working directory is exactly" prompt line partially compensates. **Fix:** add `GOOSE_WORKING_DIR` to `wslEnv` and list it in the `WSLENV` string (which itself ends with a stray `:u`).

### 4.7 Smaller observability gaps
- `warmEngine()` failures are swallowed (`catch {}`) — a post-boot ping failing is invisible; the dispatch will fail later with a first-token timeout that blames "engine wedged or saturated" without the ping having said so.
- `/metrics` scrape in `readEngineMetrics()` silently caches `null` on failure; status shows `engine: null` with no "stale/unreachable" marker.
- `sessionExistsOnDisk()` spawns the full goose binary (10 s timeout) on **every** dispatch to parse `session list` output by string splitting on `" - "` — seconds of 9p latency per dispatch and a parser that breaks on session names containing ` - `.
- `qwen_task status` for a `queued` task names the slot holder, but only from the *same* state root (§4.3) — cross-platform it reports no holder (the file isn't there), reading as "nothing is running."
